01

Cliente e servidor: um pedido, uma resposta

aula: Web APIs e HTTP · PM 3

O cliente (o navegador) pede um recurso e apresenta o resultado para quem usa. O servidor recebe o pedido, processa e devolve uma resposta. Toda conversa HTTP tem essa forma, e quem começa é sempre o cliente.

1

Cliente monta o pedido

Método, endereço e cabeçalhos: o que quer e em que formato aceita.

2

O pedido viaja

O DNS acha o endereço do servidor; a rede leva a mensagem até ele.

3

Servidor processa

Consulta os dados, decide o código de status e monta a resposta.

4

Cliente apresenta

Lê a resposta e mostra o resultado na tela de quem pediu.

tela do cliente
clique num dos botões acima

Papel do cliente

Solicita recursos (uma página, uma imagem, um JSON) e apresenta o resultado ao usuário. No front-end, o cliente é o navegador rodando o seu HTML, CSS e JavaScript.

Papel do servidor

Guarda os dados e as regras, processa cada requisição e devolve a resposta com um código de status. Não toma a iniciativa: espera ser chamado.

Armadilha: os papéis não se misturam

Cliente e servidor não são o mesmo programa nem trocam de lugar a cada mensagem. A mensagem tem sempre a mesma forma: linha inicial, cabeçalhos, uma linha em branco e o corpo (que pode estar vazio).

02

HTTP não guarda estado

aula: Web APIs e HTTP · PM 3

Para o protocolo, cada requisição é independente: o servidor não lembra do pedido anterior. Por isso quem já fez login precisa levar a identificação em todo pedido, num cookie ou num token.

consoleo servidor não lembra do pedido 3

Cada pedido chega sozinho

O pedido 4 vem logo depois do 3, do mesmo navegador, e mesmo assim recebe 401. O servidor só sabe quem é você pelo que está naquela mensagem.

Cookie ou token

A “sessão” é construída pela aplicação: o servidor entrega um identificador no login e o cliente o reapresenta a cada envio, no cabeçalho Cookie (o navegador manda sozinho) ou em Authorization.

Armadilha: “o HTTP mantém a sessão aberta”

Não mantém. Também não guarda a senha no servidor nem “invalida” a identificação a cada pedido: ele simplesmente não tem memória. Sem estado = stateless.

04

GET leva os parâmetros na URL

aulas: Web APIs e HTTP · PM 3 e AJAX · PM 4

No GET, os filtros viajam no próprio endereço, depois do ?. O endereço do resultado pode ser salvo nos favoritos, compartilhado e guardado em cache. Mude os filtros e veja a URL mudar.

previewformulário de busca: cada busca é um GET com outra URL

Leitura segura

GET pede dados sem alterar o estado do recurso. Por isso o navegador pode repetir, guardar em cache e deixar você favoritar o endereço do resultado.

Query string

Depois do ?, pares chave=valor separados por &. URLSearchParams monta e codifica: o espaço e o acento de “comédia” viram %C3%A9 sozinhos.

Armadilha: senha em GET

Tudo o que está na URL fica no histórico, nos favoritos e nos logs do servidor. Dados sensíveis vão no corpo de um POST, e o corpo só fica protegido no caminho com HTTPS.

05

Códigos de status: o primeiro dígito diz tudo

aula: Web APIs e HTTP · PM 3

Toda resposta começa com um número de três dígitos. A faixa (o primeiro dígito) diz se deu certo e de quem é a responsabilidade quando não deu. Digite um código ou clique num exemplo.

código de status


      

    


    

      
1xxinformaçãoo pedido segue em andamento

      
2xxsucesso200 OK · 201 Created · 204 No Content

      
3xxredirecionamento301 mudou de endereço · 304 use o cache

      
4xxerro do cliente400 · 401 · 403 · 404: o pedido veio errado

      
5xxerro do servidor500 · 502 · 503: o servidor falhou

    


    

      
Para quem encaminhar
4xx: quem fez o pedido corrige (URL, login, permissão, dados). 5xx: a equipe do servidor ou da infraestrutura investiga. 3xx: normalmente o navegador resolve sozinho.

      
401 x 403
401: não sei quem você é (falta login ou token). 403: sei quem você é, mas você não tem permissão. Nos dois casos o problema está no pedido.

      
Armadilha: as faixas são padrão
Os significados são definidos pela especificação do HTTP, iguais em qualquer servidor. Nem toda faixa é falha: 2xx e 3xx são respostas normais.

    

  


  
  

    

      06
      
HTTPS: o mesmo HTTP, dentro do TLS

      novo nesta revisão · visto de passagem em Web APIs e HTTP
    

    
HTTPS não é outro protocolo, com outros métodos e outros status: é o HTTP transportado sobre TLS. O TLS cifra a conversa, confere se ela não foi alterada e prova, com um certificado digital, que o servidor é quem diz ser.


    

      
1
Olá
O navegador diz quais versões do TLS e quais cifras aceita.

      
2
Certificado
O servidor apresenta um certificado assinado por uma autoridade confiável: autenticação.

      
3
Chave da sessão
Os dois combinam uma chave secreta que nunca passou pela rede.

      
4
HTTP cifrado
Os mesmos GET e POST de sempre, ilegíveis para quem está no caminho.

    


    

      

        
        
        
      

      

        

          
no navegador (edite)

          
        

        

          
o que passa pelo Wi-Fi

          

        

        

          
o que o servidor recebe

          

        

      

      
A cifra é de verdade: AES-GCM de 256 bits, da Web Crypto API do navegador, com uma chave nova a cada carga da página. É o mesmo tipo de cifra que o TLS usa depois do aperto de mão.

    


    

      
Confidencialidade
Quem intercepta vê só bytes embaralhados: nem a senha, nem o caminho /login, nem os cabeçalhos.

      
Integridade
Se 1 bit muda no caminho, a verificação falha e a mensagem é rejeitada. Sem TLS, a alteração passa despercebida.

      
Autenticação
O certificado digital prova que você fala com o servidor do domínio, e não com um impostor no meio do caminho.

      
Armadilha: TLS x SSL
TLS é o sucessor do SSL, que está obsoleto e inseguro. Porta padrão: 443 (HTTP usa 80). Criptografia vale para a conversa toda, não só para senhas nem só para pagamentos.

      07
      
Síncrono x assíncrono

      aula: Fluxo assíncrono · PM 4
    

    
O JavaScript da página roda numa thread só. Uma operação síncrona ocupa essa thread até terminar e nada mais acontece. Uma assíncrona é entregue ao navegador e o código segue; o resultado chega depois. Clique em “clique aqui” durante cada consulta.


    

      

      

        
relógio da página0,0 s

        
        
        
      

      

    


    

      
      

        
consoleo número à direita é o tempo de cada linha

        

      

    


    

      
Síncrono bloqueia
A próxima instrução só começa quando a atual termina. Numa consulta demorada, a tela congela: animação parada, cliques acumulados para depois.

      
Assíncrono não espera parado
Requisições, timers e leitura de arquivos correm “por fora”. Quando o resultado fica pronto, a função combinada (callback, .then, await) continua o trabalho.

      
Armadilha: assíncrono não é “mais rápido”
A consulta demora o mesmo nos dois casos. A diferença é que a página continua respondendo. E operações assíncronas falham do mesmo jeito: precisam de tratamento de erro.

    

  


  
  

    

      08
      
Promise: três estados, e não volta atrás

      aulas: Fluxo assíncrono e AJAX · PM 4
    

    
Uma Promise representa um valor que ainda pode não estar disponível. Ela nasce pendente e termina uma única vez: realizada, com um valor, ou rejeitada, com um motivo. Depois disso, o estado não muda mais.


    

      
      

        
previewuma Promise de verdade, nesta página

        

          

            

              
pendentepending · ainda sem valor

              

                
realizadafulfilled · tem um valor

                
rejeitadarejected · tem um motivo

              

            

            
estado:  · 

            

              
              
              
            

            

          

        

      

    


    

      
Três estados
Pendente (pending), realizada (fulfilled) e rejeitada (rejected). Realizada ou rejeitada = “resolvida” (settled).

      
Uma vez só
Resolva uma Promise e tente rejeitá-la: nada acontece. Ela não alterna entre estados nem volta a ficar pendente. Para tentar de novo, crie outra.

      
Armadilha: Promise também falha
Ser Promise não impede o erro: uma rejeição sem .catch (ou sem try...catch no await) vira Uncaught (in promise) no console.

Encadeando com .then, .catch e .finally

      aulas: Fluxo assíncrono e AJAX · PM 4
    

    
Cada .then recebe o que o anterior devolveu e devolve uma nova Promise. O .catch pega uma rejeição de qualquer ponto acima dele. O .finally roda nos dois casos.


    

      
      

        
consolea mesma cadeia, com e sem Internet

        

          

            
            
          

          

        

      

    


    

      
O retorno vira a entrada
O que um .then devolve chega no próximo. Se devolver uma Promise (como resposta.json()), o próximo espera ela terminar.

      
Um catch para a cadeia toda
Rejeição do fetch ou throw dentro de qualquer .then: tudo pula direto para o .catch mais próximo abaixo.

      
Armadilha: esquecer o return
Com chaves, .then(r => { r.json(); }) não devolve nada e o próximo .then recebe undefined. Sem chaves, a arrow function devolve sozinha.

async/await: a mesma Promise, sem .then

      aulas: Fluxo assíncrono e AJAX · PM 4
    

    
async e await são outra forma de escrever Promises. O await pausa só a função até a Promise resolver; a página continua livre. O resultado é o mesmo da cadeia de .then.


    

      

        
com .thencadeia de Promises

        
        

      

      

        
com async/awaitmesmo resultado, leitura de cima para baixo

        
        

      

      

        
async sempre devolve Promisemesmo que o return seja um número

        
        

      

      

        
await precisa de Promisesem await, você guarda a Promise, não o valor

        
        

      

    


    

      
Escrita alternativa
await p faz o mesmo que p.then(...): espera a Promise e entrega o valor. Por baixo, continua sendo Promise.

      
Pausa a função, não a página
Enquanto carregar() espera, a linha “a página segue” já rodou. await não torna nada síncrono.

      
Armadilha: await não substitui o fetch
O await espera; quem faz a requisição continua sendo o fetch. E os erros continuam existindo: trate com try...catch (próxima seção).

try...catch com await

      aulas: try...catch · PM 3 e AJAX · PM 4
    

    
Com await, uma Promise rejeitada vira uma exceção comum, que o catch pega. O throw transforma um 404 em erro também, e o finally roda sempre.

try: a ação arriscada
Coloque no try o await fetch, a conferência do status e a leitura do corpo: qualquer um dos três pode falhar.

      
catch: o resgate
Registre o erro (console.error) e mostre uma mensagem útil para quem usa. Nunca deixe o catch vazio: o erro some e ninguém descobre.

      
Armadilha: try sem await
Sem await, o try só vê a criação da Promise, que não falha. A rejeição chega depois e escapa como Uncaught (in promise).

O que chega no primeiro .then: um Response

      aula: AJAX e Intl · PM 4
    

    
A Promise do fetch resolve com um objeto Response: a descrição da resposta HTTP (status, ok, cabeçalhos, URL). Os dados ainda não estão prontos; o corpo é um fluxo que precisa ser lido.

O que o Response tem
status (200, 404…), ok (true de 200 a 299), statusText, headers, url e o body, ainda não lido.

      
Duas esperas
Primeiro chegam o status e os cabeçalhos (a Promise do fetch). Depois o corpo é baixado e convertido (a Promise do json()).

      
Armadilha: tratar o Response como os dados
Não é o array, não é o texto do corpo, não é só o número do status e não é a requisição enviada. É a resposta inteira, esperando ser lida.

      aula: AJAX e Intl · PM 4

404 e 500 não caem no catch

      aula: AJAX e Intl · PM 4
    

    
A Promise do fetch só é rejeitada quando a requisição não se completa: sem Internet, servidor fora do ar, endereço inválido. Um 404 ou um 500 é uma resposta completa, então a Promise resolve normalmente. Quem transforma isso em erro é você, conferindo ok ou status.

200, 201, 204resolvetruenão, e não deve

          
404, 401, 400 (erro do cliente)resolvefalsesó se você der throw

          
500, 502, 503 (erro do servidor)resolvefalsesó se você der throw

          
sem Internet, servidor inalcançável, URL inválidarejeita com TypeErrornão existe respostasim, sozinha

        
      

    


    

      
Por que é assim
Para o fetch, conseguir uma resposta já é sucesso: a requisição se completou. Se o conteúdo é bom ou ruim, é decisão da aplicação.

      
A regra prática
Todo fetch merece if (!resposta.ok) throw new Error(...) antes do json(), mais um catch no fim. Assim os dois tipos de falha chegam ao mesmo lugar.

Mover o .catch para antes dos .then não faz ele pegar um 404. Nem o fetch repete a requisição sozinho. O que falta é conferir o status.

Enviando dados: POST com JSON

      aula: AJAX e Intl · PM 4
    

    
Para enviar, o fetch recebe um segundo argumento com o método, os cabeçalhos e o corpo. O corpo trafega como texto: JSON.stringify transforma o objeto em texto JSON e o cabeçalho Content-Type avisa o servidor de como interpretar esse texto.

sem JSON.stringifyo objeto vira "[object Object]"

        
        

      

      

        
sem Content-Typeo servidor não sabe ler o corpo

        
        

      

    


    

      
JSON.stringify
Converte o objeto JavaScript em texto JSON. Não criptografa, não valida campos: só serializa. O caminho inverso é JSON.parse (e o json() da resposta).

      
Content-Type
Cabeçalho que diz o formato do corpo: application/json. Não define idioma nem criptografia. Sem ele, o fetch manda text/plain.

      
Armadilha: “o fetch converte sozinho”
Não converte. Objeto no body vira o texto "[object Object]", e o servidor responde 400. Os dois, stringify e Content-Type, são necessários.

timeZone: um instante, vários relógios

IIFE: a função que se executa sozinha

      novo nesta revisão
    

    
IIFE (Immediately Invoked Function Expression) é uma função definida e executada no mesmo lugar. Ela não precisa de nome nem de uma chamada depois: o par de parênteses do fim a invoca na hora.


    

      
      

        
consolequatro IIFEs, quatro execuções

        

          

          

            
(function () { … })();

            

              1º par: transforma a declaração em expressão
              a função, sem nome
              2º par: chama a função na hora
            

          

        

      

    


    

      

        
sem o primeiro par de parêntesesvira declaração, que exige nome

        
        

      

      

        
sem o par do fima função é criada, mas ninguém a chama

        
        

      

    


    

      
Para que serve
Rodar um trecho de inicialização uma vez só e, principalmente, criar um escopo isolado: o que é declarado lá dentro não vaza para o resto da página (próxima seção).

      
Onde você encontra
Em scripts legados e em bibliotecas antigas, de antes dos módulos ES6. O arquivo aula.js desta página começa com uma IIFE.

      
Armadilha: “toda função precisa de nome”
Só a declaração de função precisa. Entre parênteses, ela é uma expressão e pode ser anônima, sem precisar ser guardada numa variável.

Escopo: o que fica dentro, o que fica fora

      novo nesta revisão
    

    
Cada função cria um escopo. Quem está dentro enxerga e pode alterar as variáveis de fora; quem está fora não enxerga as de dentro. A IIFE usa essa regra para esconder variáveis do escopo global.


    

      
      

        
consoleo de fora mudou; o de dentro não aparece

        

      

    


    

      

        
mesmo nome, dentro e forao de dentro esconde o de fora

        
        

      

      

        
var global vira window.algoa IIFE não deixa vazar

        
        

      

      

        
a referência que saio que a IIFE devolve continua alcançável

        
        

      

    


    

      
De dentro para fora: sim
A função enxerga o escopo onde foi criada (escopo léxico). Por isso ingressos -= vendidos altera a variável global.

      
De fora para dentro: não
typeof de uma variável que não existe devolve "undefined", sem erro. Usá-la direto lança ReferenceError.

      
Armadilha: a IIFE não protege tudo
Ela isola o que é declarado dentro. Se o código de dentro altera uma variável de fora, ou devolve uma referência para fora, essa parte continua exposta.

Módulos: export e import com chaves

      novo nesta revisão · visto de passagem em AJAX e Intl
    

    
Desde o ES6, a linguagem tem um sistema de módulos próprio, sem biblioteca: cada arquivo é um módulo, export escolhe o que sai dele e import traz para outro arquivo. Nada vira global.


    

      

        
consolemódulos ES de verdade, rodando neste navegador

        

      

      

        
        
      

    


    

      

        
importar o que não foi exportadoo módulo nem começa a rodar

        
        

      

      

        
import { … as … }renomear na chegada

        
        

      

      

        
import * astudo o que foi exportado, num objeto

        
        

      

    


    

      
Nativo e no navegador
import e export fazem parte da linguagem e funcionam nos navegadores com <script type="module">, e também no Node.js. Não exigem biblioteca externa.

      
Exportar não esconde, publica
O que tem export fica disponível para outros arquivos; o que não tem continua privado do módulo, como arredondar. Ganha-se reutilização e organização.

      
Armadilha: abrir por duplo clique
Pelo endereço file:// o navegador bloqueia módulos. Rode com um servidor local (Live Server, por exemplo). Nesta página eles funcionam porque a demonstração os carrega por dentro.
