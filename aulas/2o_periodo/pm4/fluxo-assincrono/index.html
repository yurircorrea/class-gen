01

Código síncrono: uma instrução de cada vez

No código síncrono cada linha só começa quando a anterior termina, na ordem em que foi escrita. É previsível. Mas e se uma delas demorar muito?

consolea ordem da saída é a ordem do código

“Pedido concluído” só aparece depois que a função inteira terminou.

Previsível

Lendo de cima para baixo você sabe a ordem exata da saída. A chamada prepararPedido() só devolve o controle quando a última linha dela roda.

A maior parte do código é assim

Contas, variáveis, laços, manipulação de texto e de arrays: tudo síncrono, e está certo que seja. Responde em microssegundos.

O problema aparece quando uma linha espera

Se “Assar pizza” levasse 3 segundos, “Servir” e todo o resto esperariam 3 segundos. No navegador, isso inclui a própria tela (próxima seção).

02

O problema do bloqueio

Uma tarefa lenta e síncrona trava a página inteira. Clique em esperar(3000) e, durante os 3 segundos, tente clicar no contador e rolar a página. Depois compare com o setTimeout.

previewclique, e depois tente clicar no contador

Durante esses 3 s

Os botões não respondem, a rolagem congela e as animações param. A página inteira, não só o quadro: o JavaScript da aula e o do exemplo dividem a mesma thread.

Os cliques não se perdem

Os cliques feitos durante o bloqueio ficam guardados numa fila e são contados todos de uma vez quando o while termina. Essa fila é uma das peças da seção 05.

Uma requisição pode levar muito mais

Se buscar dados na internet fosse síncrono, a tela ficaria congelada pelo tempo da rede: 1 s, 10 s, ou para sempre se a conexão cair. Por isso esperar é sempre assíncrono no navegador.

A senha

Assíncrono é receber uma promessa de resultado e seguir em frente. Quem chama não fica parado: registra o que fazer quando o resultado chegar.

Quem espera é o navegador

O timer, a resposta da rede e o clique ficam por conta do navegador. O JavaScript só volta a agir quando há algo pronto para ele.

Armadilha: ler o resultado cedo demais

No segundo exemplo, pokemon ainda é undefined na linha seguinte, mesmo com timer de 0 ms. O valor assíncrono só pode ser usado dentro do callback, do .then ou depois do await.

04

Fato importante: uma coisa de cada vez

O JavaScript tem uma única thread principal. Assíncrono não é rodar duas funções ao mesmo tempo: é delegar a espera ao navegador e continuar trabalhando.

consoleolhe o tempo de cada linha

O timer venceu aos 0,1 s, mas só rodou depois do while: não havia outra thread para ele.

Assíncrono não é paralelo

Duas funções JavaScript nunca rodam ao mesmo tempo na mesma página. Enquanto uma está na pilha, a outra espera a vez, por mais urgente que seja.

O tempo do timer é um mínimo

setTimeout(fn, 100) quer dizer “não antes de 100 ms”. Se a thread estiver ocupada, roda mais tarde. Nunca roda antes.

Para cálculo pesado de verdade

Quando o trabalho é da CPU (processar uma imagem, um arquivo enorme), o navegador oferece outra thread: os Web Workers. Fica de fora desta aula, mas é a resposta para “e se eu precisar mesmo de um while longo?”.

05

Os bastidores: quatro peças

Quatro peças fazem o assíncrono funcionar. O JavaScript cuida de uma (a pilha); o navegador cuida das outras.

1

Call Stack

Pilha das funções em execução agora. Uma por vez: a última que entrou é a primeira que sai.

2

Web APIs

O navegador cuida da espera: setTimeout, fetch, eventos de clique.

3

Fila de tarefas

Callbacks prontos aguardando a vez de rodar, na ordem em que ficaram prontos.

4

Event Loop

Quando a pilha esvazia, leva o próximo callback da fila para ela. E repete, para sempre.

Ciclo: a pilha chama uma Web API a espera termina e o callback entra na fila o Event Loop devolve o callback à pilha
consolecada função espera a de cima sair

No passo 3 a pilha tem preparar, assar e servir, de baixo para cima.

A pilha precisa esvaziar

O Event Loop só traz um callback da fila quando não há mais nada na pilha, nem o script principal. É a regra que explica todas as ordens de saída desta aula.

Web APIs não são JavaScript

setTimeout, fetch e addEventListener são oferecidos pelo navegador. No Node.js, quem faz o mesmo papel é a biblioteca libuv.

Fila é fila

O primeiro callback a ficar pronto é o primeiro a rodar. A exceção são as promises, que têm uma fila só delas (seção 07).

Event Loop:

“Assim que possível”, não “agora”

setTimeout(…, 0) coloca o callback na fila logo que pode. Mas a fila só anda quando a pilha esvazia, e a pilha só esvazia quando o script inteiro termina.

O script também ocupa a pilha

O código solto do arquivo (o “script”) é a primeira coisa na pilha. Enquanto houver uma linha dele para rodar, nenhum callback entra.

Armadilha: 0 ms nunca é exato

Além de esperar a pilha, o navegador pode atrasar o timer: depois de cinco setTimeout aninhados, o mínimo vira 4 ms, e abas em segundo plano esperam até 1 s.

Duas filas: promises passam na frente dos timers

Os callbacks de promises não entram na mesma fila dos timers. Eles têm uma fila própria, a de microtarefas, que tem prioridade.

Event Loop:

Microtarefas

Callbacks de promises (.then, .catch, o que vem depois de um await) e queueMicrotask. A fila é esvaziada inteira sempre que a pilha fica vazia.

Tarefas (macrotarefas)

setTimeout, setInterval e eventos. Uma por volta do Event Loop. A especificação do HTML chama só de “tarefas”; “macrotarefa” é o apelido que a comunidade usa.

Armadilha: microtarefa sem fim trava a tela

Como a fila de microtarefas é esvaziada inteira, uma promise que agenda outra promise para sempre nunca deixa a vez para os cliques nem para o desenho da tela. O efeito é o mesmo do while da seção 02.

Resumo da Aula 1

O JavaScript executa uma instrução por vez na Call Stack. Tarefas demoradas ficam com o navegador, nas Web APIs. O Event Loop devolve os callbacks à pilha quando ela fica vazia.

Prioridade

Microtarefas (promises) rodam antes de tarefas (timers), mesmo que o timer tenha sido criado antes e seja de 0 ms.

Armadilha: confiar na ordem entre timers diferentes

Entre dois timers, quem vence primeiro roda primeiro, não quem foi escrito primeiro. Se a ordem importa, encadeie: faça o segundo começar dentro do primeiro, ou use promises.

09

No dia a dia: onde o assíncrono aparece no front-end

Requisições, timers e eventos são assíncronos. O localStorage, que vai aparecer muito na Pokédex, não é.

fetchbusca dados sem travar a tela

Nesta página, um servidor simulado responde em 0,4 s.

setIntervalagenda código para depois, de novo e de novo
addEventListenerroda quando o usuário age
localStoragesíncrono: responde na hora, sem await

Três fontes de “depois”

Requisições (fetch), timers (setTimeout, setInterval) e eventos (addEventListener). Em todos, você entrega uma função e o navegador chama quando for a hora.

localStorage é síncrono

getItem e setItem respondem na hora, sem await. Funciona porque os dados são poucos e ficam no próprio computador.

Armadilha: localStorage só guarda texto

O número 25 voltou como o texto "25". Para guardar um array ou um objeto, use JSON.stringify ao salvar e JSON.parse ao ler (seção 21).

11

Callbacks: uma função para ser chamada depois

Um callback é uma função entregue a outra para ser chamada quando a tarefa terminar. A busca simulada avisa quando acaba chamando o callback.

consoleusando a busca

Erro primeiro

O callback recebe (erro, dados). Se deu certo, erro é null. É uma convenção muito usada no Node.js: quem chama é obrigado a olhar o erro antes dos dados.

“Buscando…” aparece primeiro

A busca é assíncrona: buscarPokemonCB só agenda o timer e devolve o controle. O código segue e o callback roda 1 s depois.

Armadilha: esquecer o return

Sem o return depois de callback(erro), a função continua e chama o callback uma segunda vez, agora com pokemon indefinido. O mesmo vale dentro do callback de quem usa.

12

O problema: callback hell

Para montar um time de três Pokémon, cada busca vai dentro do callback da anterior. O código anda para a direita e o tratamento de erro se repete em cada nível.

consoletrês buscas, uma depois da outra

3 s para três buscas que não dependem uma da outra.

Pirâmide da perdição

Cada nível de espera é um nível de indentação. Com cinco buscas o código fica ilegível, e mexer na ordem significa reescrever a pirâmide.

Uma espera de cada vez

As três buscas são independentes, mas cada uma só começa quando a anterior termina: 3 s em vez de 1 s. Com promises dá para disparar as três juntas (seção 22).

Armadilha: checar o erro só no fim

Um atalho comum é um único if (e1 || e2 || e3) return; no nível mais fundo. Se a primeira busca falha, as outras rodam mesmo assim e o erro some sem mensagem. Cada nível precisa do seu teste.

13

Iterators: next() devolve { value, done }

Um iterator percorre uma coleção um item por vez, sob demanda. Cada chamada de next() entrega o próximo item, até done virar true.

consoleo mesmo iterator, chamada após chamada
for…ofusa o mesmo protocolo por baixo
for…of em objetoobjeto comum não é iterável

next()

Cada chamada entrega um objeto { value, done }. Enquanto done é false, value traz o item; no fim, value é undefined.

for…of

Chama next() por você até done ser true. Funciona em arrays, strings, Map, Set e em qualquer objeto que tenha [Symbol.iterator].

Armadilha: for…of em objeto comum

Objeto literal não tem [Symbol.iterator]: dá TypeError. Para percorrer as propriedades, use Object.entries, Object.keys ou for…in.

14

Geradores: function* e yield

Uma função geradora cria um iterator. Ela para em cada yield e só continua no próximo next(): ótimo para um botão “Próximo” na Pokédex.

consoleum Pokémon de fogo por clique
yieldpausa e continua
.values().filter()novidade: métodos de iterator (ES2025)

Chrome 122+, Firefox 131+ e Safari 18.4+. Em navegador antigo: TypeError.

Pausa e continua

Chamar contar() não roda nada: só cria o iterator. Cada next() roda até o próximo yield e para ali, lembrando onde estava.

Sob demanda

O gerador só procura o próximo Pokémon de fogo quando alguém pede. Com uma lista enorme, nada é processado à toa.

Novidade: métodos de iterator

Desde 2025, todo iterator tem .filter, .map, .take e outros, também sob demanda: take(3) para de procurar no terceiro. Para um filtro simples, substitui o gerador.

15

Promises: três estados possíveis

Uma promise é um objeto que representa um valor que ainda vai chegar. Ela nasce pending e muda uma única vez: para fulfilled ou para rejected.

previewclique e acompanhe o estado
pending fulfilled rejectedos três estados
EstadoSignificaQuem recebe
pendingPendente: a operação ainda está em andamentoninguém, ainda
fulfilledResolvida: deu certoo valor vai para .then()
rejectedRejeitada: deu erradoo erro vai para .catch()
resolve duas vezessó a primeira mudança vale

Um objeto, não o valor

buscarPokemon(25) devolve na hora uma promise pendente. O Pokémon chega depois, dentro do .then.

Muda uma vez só

Depois de resolvida ou rejeitada (“settled”, encerrada), a promise não volta atrás. Quem chamar .then mais tarde recebe o mesmo valor, na hora.

Por isso não há corrida

Com callback, nada impede uma função de chamar o callback duas vezes (seção 11). Com promise, a segunda chamada de resolve é simplesmente ignorada.

16

Transformando a busca em promise

A função não recebe mais callback: ela devolve uma promise, e quem chama decide o que fazer com .then e .catch.

consolequem chama decide

resolve e reject

O new Promise recebe uma função com dois controles: resolve(valor) quando deu certo, reject(erro) quando deu errado. O setTimeout continua lá dentro.

Mesma convenção de erro

Rejeite sempre com um new Error(...), como no callback. Quem trata tem name, message e stack.

Armadilha: promise rejeitada sem .catch

O terceiro botão busca o 99 sem .catch: o erro aparece como Uncaught (in promise). Toda promise que pode falhar precisa de alguém que trate a falha.

17

Encadeando com .then, .catch e .finally

Cada .then recebe o que o anterior retornou. Um único .catch trata o erro de qualquer etapa e o .finally roda nos dois casos. Sem pirâmide.

consoleo erro de qualquer etapa cai no mesmo catch

Com 99 na primeira busca, o primeiro .then é pulado inteiro: a segunda busca nem começa.

return esquecidoo próximo .then não espera nada
.then dentro de .thena pirâmide voltou

Retorne para encadear

Se o .then retorna uma promise, o próximo .then espera por ela. Se retorna um valor comum, o próximo recebe o valor na hora.

Um catch para todos

Um erro em qualquer etapa pula os .then seguintes e cai no .catch. O tratamento fica num lugar só, ao contrário da pirâmide.

Armadilha: esquecer o return

Sem return, a segunda busca roda solta: o próximo .then recebe undefined na hora, e se ela falhar, o .catch da corrente não fica sabendo.

Combinando várias promises

Quatro métodos esperam várias promises ao mesmo tempo. Escolha pelo que você precisa quando uma delas falha.

A ordem do resultado é a ordem do pedido

Promise.all devolve os valores na ordem do array de entrada, não na ordem em que cada um ficou pronto.

race x any

No último exemplo, a falha de 200 ms vence a race (que fica com a primeira a terminar, mesmo com erro). A any ignora a falha e espera o Pikachu.

Armadilha: quando todas falham

Promise.any só rejeita se todas falharem, com um AggregateError que guarda a lista de erros em .errors. Promise.allSettled nunca rejeita.

19

async / await: esperando a promise sem .then

async e await são promises com cara de código síncrono. A função para no await até a promise terminar, e os erros são tratados com try/catch.

consolea mesma busca, sem .then
await pausa a funçãonão a página
async sempre devolve promisemesmo com return de um número
esquecer o awaito erro mais comum
await fora de asynco script nem começa

Regras

await só funciona dentro de função async ou no topo de um módulo (<script type="module">). Uma função async sempre devolve uma promise. Erros são tratados com try/catch.

Pausa a função, não a página

No await, a função sai da pilha e o resto do código continua. O que vem depois do await volta como microtarefa quando a promise termina.

Armadilha: esquecer o await

Sem await, a variável guarda a promise pendente, não o Pokémon: pokemon.nome dá undefined sem erro nenhum. É o bug mais comum com async.

Callback

Simples para uma espera só. Com várias, aninha e repete o tratamento de erro em cada nível.

Promise

Encadeia em vez de aninhar e trata erros num .catch só. Também é o que permite combinar com Promise.all.

A mesma promise por baixo, lida de cima para baixo como código síncrono. É o estilo mais usado hoje; .then continua útil em cadeias curtas.

Dois awaits

22

Em sequência ou em paralelo?

Três buscas de 1 s cada. Com um await por volta do laço, levam cerca de 3 s; disparadas juntas com Promise.all, cerca de 1 s.

for…of + awaitem sequência: cerca de 3 s
Promise.allem paralelo: cerca de 1 s
forEach + awaitnão espera ninguém

Sequência: quando uma depende da outra

Se a segunda busca precisa do resultado da primeira (o id da evolução, por exemplo), o await dentro do laço é o certo.

Paralelo: quando são independentes

Um time de três Pokémon não depende de ordem. Disparar as três buscas juntas e esperar com Promise.all leva o tempo da mais lenta.

Armadilha: await dentro de forEach

O forEach chama a função async e não espera a promise que ela devolve. O código seguinte roda com o time vazio. Use for…of ou Promise.all.

23

Limite de tempo com Promise.race

Uma promise que rejeita depois de alguns milissegundos vira um cronômetro. Na corrida com a busca, quem terminar primeiro decide. Com a API levando 1 s, um limite de 500 ms faz a busca perder.

consoleajuste os tempos e observe

Quem chega primeiro

Com 500 ms, o cronômetro rejeita antes da busca resolver: “Tempo esgotado”. Com 1500 ms, a busca vence. Com o 99, a busca falha antes do limite e a mensagem é a dela.

A perdedora continua rodando

Promise.race só ignora o resultado de quem perdeu. A busca de 1 s continua até o fim; o timer de 1500 ms também. Nada é cancelado.

Com fetch de verdade: AbortSignal.timeout

fetch(url, { signal: AbortSignal.timeout(500) }) cancela a própria requisição depois de 500 ms e rejeita com TimeoutError. Funciona em todos os navegadores atuais.
