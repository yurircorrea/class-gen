01

A World Wide Web

Proposta por Tim Berners-Lee em 1989, no CERN, para pesquisadores de vários países lerem os trabalhos uns dos outros. Duas ideias explicam o sucesso: os documentos são distribuídos por servidores do mundo todo e vinculados entre si por hipertexto.

Distribuída

Cada servidor publica as próprias páginas e as anuncia a todos, sem sobrecarregar meia dúzia de servidores centrais. É o que permite a Web crescer.

Vinculada

Um link aponta para um documento guardado em qualquer servidor do mundo. Esse texto com ligações é o hipertexto, o "HT" de HTTP e de HTML.

Abra o F12

Na aba Rede (Network) das ferramentas do navegador, recarregue qualquer site: uma página comum faz dezenas de pedidos (HTML, CSS, scripts, imagens, fontes).

02

O navegador: o cliente Web

Todo navegador tem três partes: o controlador recebe o que você digita e clica, o protocolo cliente busca o documento e o interpretador transforma o código-fonte em página na tela.

preview a mesma página, depois do interpretador

1 controlador: barra de endereço, cliques, teclado 2 protocolo cliente: HTTP ou HTTPS 3 interpretador: desenha a página acima

Mesmo arquivo, duas leituras

O servidor envia só texto. Quem decide que <b> vira negrito é o interpretador do navegador. Pelo F12 você vê o fonte; na tela, o resultado.

Interpretadores de hoje

HTML, CSS, JavaScript e WebAssembly. O motor muda de navegador para navegador: Chromium (Chrome, Edge, Opera), Gecko (Firefox) e WebKit (Safari).

Navegadores que saíram de cena

Internet Explorer (encerrado em 2022) e Netscape (2008) não existem mais, e applets Java deixaram de rodar nos navegadores. FTP também saiu da lista de protocolos do navegador (ver seção 17).

03

O servidor Web

O servidor guarda as páginas e responde a cada pedido. Para dar conta de muitos clientes, ele guarda em cache os arquivos mais pedidos e atende vários pedidos ao mesmo tempo (multithreading).

em fila, cerca de 5 s; ao mesmo tempo, pouco mais de 1 s: o servidor atendeu os cinco em paralelo

Cache

Ler da memória é muito mais rápido que ler do disco. O servidor guarda ali os arquivos pedidos com frequência e responde sem ir ao disco.

Vários ao mesmo tempo

Com várias threads ou processos, o servidor não deixa um cliente esperando o outro terminar. Foi o que a barra "ao mesmo tempo" mostrou.

Servidores de hoje

Apache e IIS dominaram os anos 2000. Hoje Nginx, Apache e Cloudflare dividem a maior parte da Web, e o IIS ficou bem atrás. Numa API, o "servidor" costuma ser a própria aplicação: Node.js, Spring Boot, ASP.NET.

URL: o endereço de um recurso

Para achar uma página são precisos quatro identificadores: o protocolo (como buscar) e o trio host, porta e caminho (onde está). Digite qualquer endereço e veja cada parte.

Host

Pode ser um IP (64.23.56.17) ou um nome de domínio (viacep.com.br). O nome precisa ser traduzido em IP pelo DNS antes do pedido sair (seção 15).

Porta

Número de 16 bits que diz qual programa do servidor atende. Quando é a padrão do protocolo, fica implícita: http usa 80 e https usa 443.

Porta 80 ou 443?

Durante muito tempo a porta padrão da Web foi a 80, do HTTP sem criptografia. Hoje quase todo site usa HTTPS, porta 443. E a URL tem mais duas partes: ?consulta (parâmetros que vão ao servidor) e #fragmento (que nunca sai do navegador).

Estático

Rápido e barato de servir, mas o cliente só recebe uma cópia. Esta aula, publicada no GitHub Pages, é um documento estático.

Dinâmico

Antes era CGI, PHP, ASP. Hoje o servidor de uma API gera JSON a cada pedido: é o que você vai consumir na seção 22.

Os três juntos

Um site moderno é um documento ativo (JavaScript no navegador) que busca dados dinâmicos em uma API, servido a partir de arquivos estáticos.

06

HTTP: um pedido, uma resposta

O HTTP (HyperText Transfer Protocol) define como cliente e servidor conversam: o cliente envia uma solicitação, o servidor devolve uma resposta. Sem pedido, não há resposta. Envie o primeiro.

preview requisição real jsonplaceholder.typicode.com
a resposta é um usuário fictício de uma API de treino

O cliente fala primeiro

O servidor nunca inicia a conversa: ele fica esperando pedidos. Cada pedido recebe exatamente uma resposta.

Portas dos dois lados

O servidor escuta numa porta conhecida (443 em HTTPS, 80 em HTTP). O cliente usa uma porta temporária, sorteada pelo sistema operacional para aquela conexão.

Texto que se lê

As mensagens que você viu acima são texto puro, linha por linha. É por isso que dá para ler, escrever e depurar HTTP à mão.

07

Formato das mensagens

Pedido e resposta têm quatro partes. Só a primeira linha muda de nome: linha de solicitação no pedido, linha de estado na resposta. Depois vêm os cabeçalhos, uma linha em branco e o corpo.

preview as quatro partes, contornadas

mensagem de pedido

mensagem de resposta

A linha em branco é obrigatória

É ela que diz "acabaram os cabeçalhos". Sem ela, o servidor não sabe onde começa o corpo. No fio são dois pares CR LF seguidos.

Corpo é opcional

Um GET normalmente não leva corpo; um POST leva. A resposta 204 No Content e a 304 Not Modified também vêm sem corpo.

CR LF, não só LF

No HTTP/1.1 cada linha termina com dois caracteres: \r\n. Quem escreve um servidor "na mão" e usa só \n recebe pedidos que alguns clientes não entendem.

O método é a primeira palavra da linha de solicitação. Envie cada um para um servidor de eco, que devolve no corpo da resposta exatamente o pedido que recebeu.

HEAD: só os cabeçalhos

Compare o HEAD com o GET acima: mesmo status, mesmo Content-Length, corpo vazio. É o jeito de perguntar "quanto pesa?" sem baixar.

O preflight do CORS

Antes de um PUT, PATCH ou DELETE para outro site, o navegador manda sozinho um OPTIONS perguntando se pode. A nota abaixo da resposta avisa quando isso aconteceu.

Nem todo método é para você

TRACE virou risco de segurança e o navegador se recusa a enviá-lo (teste o botão). CONNECT só faz sentido para proxies. No dia a dia de uma API você vai usar GET, POST, PUT, PATCH e DELETE.

Host, Cookie, Origin, Content-Length, Date e outros são controlados pelo navegador. Um script não consegue falsificá-los.

Host não é o cliente

Um erro comum é achar que Host identifica quem fez o pedido. Ele traz o nome e a porta do servidor de destino. É ele que permite um mesmo IP hospedar vários sites.

Content-Type decide a leitura

text/plain, text/html, application/json, image/png: é por ele que o cliente sabe se deve exibir, interpretar ou baixar o corpo.

Content-Length = 16

No exemplo do Apache, "This is a test." tem 15 caracteres mais a quebra de linha: 16 bytes. O cliente lê exatamente esse tanto de corpo.

O JavaScript não vê tudo

Numa resposta de outro site, o script só lê Content-Type, Content-Length, Cache-Control, Content-Language, Expires, Last-Modified e Pragma, mais os que o servidor liberar em Access-Control-Expose-Headers. Set-Cookie, nunca.

11

Códigos de status

A linha de estado traz um número de três dígitos que diz como o pedido terminou. O primeiro dígito já conta a história: deu certo, vá para outro lugar, você errou ou eu errei.

preview requisição real servidor de eco: GET /status/código devolve o código pedido
1xxinformativo

Respostas provisórias, como 100 Continue e 101 Switching Protocols. Ficam entre o navegador e o servidor: o JavaScript nunca as recebe.

2xxsucesso
3xxredirecionamento
4xxerro do cliente
5xxerro do servidor

fetch não lança erro em 404

Para o fetch, uma resposta 404 ou 500 é uma resposta como outra qualquer. Ele só lança erro quando nenhuma resposta chega. Confira r.ok ou r.status.

3xx: o navegador segue sozinho

Clique em 301 ou 302: o servidor manda um Location e o navegador faz um segundo pedido para lá. O que chega ao script já é a resposta final, com "redirecionado para".

Bem mais que 200, 400 e 404

Esses três são os mais conhecidos, mas uma API usa pelo menos 201, 204, 401, 403, 409 e 500. Na dúvida, o primeiro dígito decide: 4xx é culpa de quem pediu, 5xx é culpa de quem respondeu.

Negociação de conteúdo

O cliente diz o que aceita (Accept), o servidor diz o que mandou (Content-Type). Vale para imagem, idioma (Accept-Language) e para escolher entre JSON e XML numa API.

PUT envia o documento inteiro

No segundo exemplo o corpo do pedido é a página. Por isso o pedido precisa de Content-Type e Content-Length, como a resposta. CGI (/cgi-bin) é a forma antiga de gerar páginas; hoje seria uma rota da aplicação.

Três armadilhas ao escrever à mão

Tipos MIME são sempre em inglês: image/gif, nunca "imagem/gif". Content-Encoding diz a compressão (gzip, br), não a versão do MIME; MIME-Version é um cabeçalho de e-mail. E a data HTTP não leva hífens: 10 Jan 2011.

13

Pedido condicional

O cliente pode pedir: "só me mande se mudou". Se não mudou, o servidor responde 304 Not Modified sem corpo, e o cliente usa a cópia que já tem. Faça os passos na ordem.

pela data: If-Modified-Since

O passo 2 reaproveita o Last-Modified que chegou no passo 1.

pela versão: ETag e If-None-Match

304 economiza banda

Compare o tamanho do corpo nos passos 1 e 2: a segunda resposta chega vazia. Em imagens e scripts grandes, isso deixa a página muito mais rápida.

ETag: a forma mais usada hoje

Em vez da data, o servidor dá uma "impressão digital" da versão (ETag). O cliente devolve em If-None-Match; se for igual, 304. O navegador faz isso sozinho com o cache.

Data no formato certo

O HTTP exige Thu, 04 Sep 2008 00:00:00 GMT: dia da semana, dia, mês em três letras, ano, hora e GMT. Sem o ano ou com o mês em quatro letras ("Sept"), o servidor não entende a condição.

Atributos de segurança
HttpOnly: o JavaScript não lê. Secure: só viaja em HTTPS. SameSite: não vai junto em pedidos vindos de outros sites. Max-Age: validade em segundos.

      
Por que este quadro não usa uma API pública
Um cookie criado por outro site enquanto você está aqui é um cookie de terceiros, e os navegadores bloqueiam esse tipo para impedir rastreamento. Por isso o teste usa o próprio domínio da aula.

      
Cookie não é segredo
Por muito tempo se disse que só o servidor lê o cookie. Hoje o JavaScript lê com document.cookie (se não for HttpOnly) e qualquer pessoa vê no F12. Por isso não se guarda nome ou documento no cookie: só um identificador de sessão (LGPD).

A semântica não mudou
Métodos, códigos de status e cabeçalhos são os mesmos da 1.0 até a 3. O que muda é como os bytes viajam: texto linha por linha na 1.1, quadros binários na 2 e na 3.

      
HTTP/2 e HTTP/3 não têm frase
Nas versões novas a linha de estado não leva "OK" nem "Not Found": só o número. As ferramentas mostram a frase por costume.

      
HTTP/1.1 não é mais o padrão
Durante anos a Web falou HTTP/1.0 e 1.1. Hoje a maioria dos sites grandes responde em HTTP/2 ou HTTP/3, e o HTTP/1.0 praticamente sumiu.

Respostas de três dígitos
220, 331, 230, 226: o FTP já usava códigos numéricos em texto, como o HTTP. 2xx é sucesso, 3xx pede mais informação, 4xx e 5xx são falhas.

      
Esconde as diferenças
O FTP copia arquivos entre computadores com sistemas operacionais diferentes sem que o usuário precise saber como cada um guarda seus arquivos.

      
O FTP saiu do navegador
Chrome e Firefox removeram o suporte a ftp:// em 2021. A senha do FTP viaja em texto puro: hoje se usa SFTP (sobre SSH) ou FTPS, e na Web o upload é um POST em HTTPS.

SMTP só envia
Transferência é "de qualquer usuário para qualquer caixa". Um SMTP pode entregar a mesma mensagem a vários destinatários do mesmo servidor de uma vez.

      
POP3 x IMAP
Acesso é "um usuário e a própria caixa". POP3 baixa e costuma apagar do servidor; IMAP deixa lá e sincroniza celular, notebook e Web.

      
E o webmail?
No Gmail ou no Outlook pelo navegador, entre você e o servidor quem fala é o HTTPS, com uma API. O SMTP continua entre os servidores. Hoje todos esses protocolos usam TLS (portas 587, 465, 993, 995).

objeto{"cidade": "Foz do Iguaçu"}chaves sempre entre aspas duplas; sem vírgula depois do último par

        
      

    


    

      
Texto, não objeto
No fio, JSON é só texto. JSON.stringify(obj) transforma o objeto em texto para enviar; JSON.parse(texto) ou resposta.json() faz o caminho de volta.

      
Content-Type: application/json
É o cabeçalho que avisa o servidor de que o corpo é JSON. Sem ele, muitos servidores ignoram o corpo inteiro (teste na seção 24).

      
Aspas curvas quebram o JSON
Word, PowerPoint e muitos editores trocam as aspas retas por curvas sozinhos: “id” : 1. JSON copiado de lá vira erro de sintaxe. Teste o botão "aspas curvas".

PUT x PATCH
Clique em PUT e veja a resposta: só sobram firstName, lastName e id, porque o PUT troca o recurso inteiro. O PATCH devolve o usuário completo (nome, e-mail, endereço), só com o campo enviado a mais.

      
Uma API que finge
A JSONPlaceholder responde como se gravasse, mas não grava nada: o POST devolve sempre o id 11, e um GET em /users/11 logo depois dá 404. Ótima para treinar, sem estragar dados de ninguém.

      
Os quatro problemas do POST
A linha inicial não traz a versão e usa a URL completa (forma de proxy). O POST com JSON vai sem Content-Type. O Location aponta para o id 2, mas o corpo diz 3. E a frase é Created, não "CREATED". Postman-Token é só do Postman, não do HTTP.

Juntando as peças: verbos, CRUD e idempotência

    

    
POST cria, GET busca (para não esquecer: POST Malone, GET Malone). Cada verbo corresponde a uma operação do CRUD e tem duas propriedades que importam para quem escreve o cliente: ser seguro e ser idempotente.


    

      

        

          
MétodoObjetivoCRUDCorpo no pedidoIdempotente¹Seguro²Ao vivo

          
            
GETObter um recurso ou grupoReadNãoSimSim 

            
POSTCriar um novo recursoCreateSimNãoNão 

            
PUTAtualizar um recurso inteiroUpdateSimSimNão 

            
DELETEDeletar um recursoDeleteNãoSimNão 

            
PATCHAtualizar parcialmente um recursoUpdateSimNãoNão 

          
        

      

      

        
        requisição real
        ¹ repetir o mesmo pedido não muda mais nada no servidor depois da primeira vez · ² só lê, não pede mudança
      

      


      
    


    

      
Seguro = só leitura
GET (e HEAD, OPTIONS) não deve alterar nada. Por isso buscadores e navegadores podem fazer GET sozinhos, para pré-carregar páginas, sem medo de apagar algo.

      
Idempotente = pode repetir
A rede caiu e você não sabe se o pedido chegou? Um PUT ou um DELETE pode ser reenviado sem efeito extra. Um POST repetido pode cobrar o cartão duas vezes.

      
PATCH: "Não" quer dizer "não garantido"
Um PATCH que troca o e-mail é idempotente; um que soma 10 ao saldo não é. A tabela marca "Não" porque o HTTP não garante. E o DELETE repetido continua idempotente mesmo devolvendo 404: o estado do servidor é o mesmo.

APIs: Application Programming Interface

    

    
"Conjunto de padrões de programação que possibilitam a construção de aplicações, a comunicação entre elas e sua utilização sem a necessidade de conhecer a maneira como foram implementadas" (Pressman, 2016). Teste uma API brasileira de verdade.

Você usou sem saber como foi feito
Não sabemos em que linguagem o ViaCEP foi escrito nem que banco usa. Basta conhecer o contrato: a URL, o método e o formato da resposta. Isso é uma API.

      
Um back-end, vários clientes
Site, aplicativo de celular e integração com outro sistema chamam a mesma API. É por isso que separar interface e dados (cliente-servidor) compensa.

      
Nem toda API usa o status direito
Para um CEP que não existe, o ViaCEP responde 200 OK com "erro": "true" no corpo, em vez de 404. Ao consumir uma API, leia a documentação e confira o corpo, não só o status.

    

  


  
  

    

      23
      
REST e RESTful

    

    
REST (REpresentational State Transfer) é o estilo de arquitetura proposto por Roy Fielding em 2000, na tese de doutorado dele, baseado em HTTP e definido por restrições. REST é o estilo; RESTful é o sistema que segue esses princípios.


    

      
cliente-servidorinterface separada dos dados
O site e o app só conhecem a API. Viu na seção 22.

      
interface uniformemensagens autodescritivas
Recursos com URL (/users/1) e ações pelos verbos HTTP. Viu nas seções 20 e 21.

      
sem estadocada pedido leva tudo
O servidor não lembra do pedido anterior: o token vai em todo pedido. Teste abaixo.

      
cacherespostas reaproveitáveis
Cache-Control, ETag e o 304. Viu nas seções 10 e 13.

      
sistema em camadasintermediários invisíveis
Balanceadores e proxies no caminho: os cabeçalhos "infraestrutura" da seção 09.

      
código sob demandaopcional
O servidor pode mandar código para o cliente rodar, como o JavaScript dos documentos ativos (seção 05).

401: quem é você?
Sem o cabeçalho Authorization, o servidor responde 401 Unauthorized. Ele não "lembra" que você já mandou o token antes: cada pedido se identifica sozinho.

      
Sem estado escala
Como nenhum servidor guarda a conversa, qualquer um de dez servidores atrás de um balanceador pode atender o próximo pedido.

      
Cinco ou seis restrições?
Muitas listas mostram só cinco. Fielding define seis, e a sexta, código sob demanda, é a única opcional.

Ferramentas do mercado
Postman e Insomnia guardam coleções de pedidos; o Swagger UI gera esta mesma tela a partir da documentação OpenAPI da API; o curl faz tudo no terminal.

      
F12, aba Rede
Com as ferramentas do navegador abertas, cada envio daqui aparece na lista com todos os cabeçalhos, inclusive os que o JavaScript não consegue ler, e o tempo de cada etapa.

      
Erro de CORS não é erro da API
Se o console disser "blocked by CORS policy", a API respondeu, mas não autorizou páginas de outro site a ler a resposta. O mesmo pedido funciona no curl ou no Postman, que não são navegadores.

Cliente de uma API de usuários

    

    
Construa uma página que faz o CRUD completo na JSONPlaceholder (/users) com fetch, mostrando o código de status de cada pedido e avisando quando algo dá errado.


    

      

        Parte 1 · obrigatória
        
O que a página precisa fazer

        
    
          
  • Listar: ao clicar em "Carregar", GET /users e uma tabela com nome, e-mail e cidade.
    • 
          
  • Detalhar: um campo de id e GET /users/{id} mostrando telefone e empresa.
    • 
          
  • Criar: formulário com nome e e-mail que envia POST /users com Content-Type: application/json e o corpo em JSON.stringify; a nova linha aparece com o id devolvido.
    • 
          
  • Editar: trocar só o e-mail com PATCH /users/{id}.
    • 
          
  • Excluir: DELETE /users/{id} e remover a linha.
    • 
          
  • Registro: para cada pedido, uma linha "MÉTODO caminho → código frase (ms)".
    • 
        

      

      
    


    

      

        Parte 2 · desafio
        
Exigências que quebram a solução preguiçosa

        
    
          
  • Buscar o id 999 mostra "Usuário não encontrado". O fetch não lança erro em 404: use resposta.ok ou resposta.status.
    • 
          
  • Sem Internet, nada é enviado: confira navigator.onLine antes e mostre um aviso; se o fetch lançar TypeError, mostre "servidor inacessível".
    • 
          
  • Todo pedido desiste depois de 8 segundos, com AbortController, e avisa o usuário.
    • 
          
  • Paginação de 5 em 5 com ?_page=1&_limit=5, mostrando o total lido do cabeçalho X-Total-Count.
    • 
          
  • O formulário não envia nome vazio nem e-mail sem @: o servidor nunca recebe um pedido que ele recusaria.
    • 
          
  • Proibido: XMLHttpRequest, jQuery, axios ou qualquer biblioteca. Só fetch.
    •
