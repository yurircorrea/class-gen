01

Erros em JavaScript: o inesperado acontece

Um erro é uma situação inesperada que interrompe o programa. Um caractere a mais num texto vindo de fora e o resto do código simplesmente não roda.

consolea chave notas está sem aspas

Nem a média nem “Boletim pronto!” aparecem: o script parou na linha 3.

Nem todo problema vira erro

consoleo JavaScript devolve um valor e segue em frente

Consequências

O programa para, o usuário fica diante de uma tela que não responde e o que estava sendo feito (um cadastro, um pagamento) pode se perder.

Por que tratar erros

Para manter a aplicação estável, dar um retorno claro a quem usa e deixar uma pista para quem vai depurar.

Armadilha: Infinity e NaN não são erros

Dividir por zero dá Infinity, conta com texto dá NaN e propriedade inexistente dá undefined. Nada é lançado, então nenhum catch é acionado. Quando esses casos importam, é você quem lança o erro (seção 07).

02

Os tipos de erro

Todo erro tem um nome que diz a causa. Os três que você mais vai ver são ReferenceError, TypeError e SyntaxError.

ReferenceErrorusar um nome que não existe
TypeErrorusar um valor do jeito errado
SyntaxErrortexto que não segue a regra
RangeErrornúmero fora do intervalo aceito
SyntaxErrorno seu próprio código: o catch nunca chega a existir
TipoQuando apareceExemplo
ReferenceErrorNome de variável ou função que não existe (ou usado antes do let).console.log(totl)
TypeErrorOperação que o tipo do valor não permite: propriedade de null, chamar o que não é função.null.nome, (7).toUpperCase()
SyntaxErrorCódigo ou texto fora da regra. No seu código, impede o script de começar; em JSON.parse, acontece durante a execução.JSON.parse("{x}")
RangeErrorNúmero fora do intervalo aceito."-".repeat(-1), new Array(-1)
URIErrorEndereço com codificação inválida.decodeURIComponent("%")
AggregateErrorVários erros de uma vez.Promise.any([...]) quando todas falham
ErrorO tipo base de todos. É o que você usa para lançar os seus.throw new Error("...")

O nome diz a causa

Antes de ler a mensagem, leia o tipo: ReferenceError é nome errado, TypeError é valor errado, SyntaxError é texto ou código fora da regra.

Todos são objetos Error

TypeError, RangeError e os outros herdam de Error. Por isso todos têm name, message e stack.

Armadilha: SyntaxError no seu código

Se o próprio arquivo tem um erro de sintaxe, o navegador nem começa a rodar o script, então o try e o catch não existem ainda. Veja o último exemplo: “capturado!” nunca aparece. O try...catch só pega SyntaxError criado durante a execução, como o de JSON.parse.

03

Sem try...catch: o risco da interrupção

Quando um erro não é tratado, a execução é interrompida e as linhas seguintes simplesmente não rodam. O programa para de forma abrupta na linha do erro.

passo a passosiga a execução linha a linha

Para o script inteiro

Um erro não tratado interrompe tudo o que vem depois naquele script: as linhas da função e as linhas de fora dela.

A página não trava, o recurso quebra

No navegador, os outros scripts e os outros botões continuam funcionando. Só aquele recurso deixa de responder, sem aviso nenhum para quem está usando.

Armadilha: funciona no teste, quebra no uso

No teste, dados sempre chega preenchido. Na vida real chega null de um campo vazio, de um servidor fora do ar ou de um JSON incompleto.

04

A solução: try...catch

No try fica o código que pode gerar um erro; no catch, o código que lida com o erro. Escolha um cenário e siga as três regras do fluxo de execução.

passo a passoum JSON válido e um inválido

1. O try roda normalmente

O código dentro do try é executado linha a linha, como qualquer outro código.

2. Erro: o try para e vai para o catch

Na linha em que um erro acontece, o try é abandonado e o controle salta para o catch, que recebe o erro.

3. Sem erro: o catch é ignorado

Se o try termina sem erro, o bloco catch é totalmente pulado. Nos dois casos o programa continua depois dele.

05

Bloco try: onde a ação acontece

O try contém o código que você quer monitorar. Qualquer erro dentro dele interrompe o bloco e aciona o catch.

tryuma variável que não existe
let dentro do trysó existe dentro do bloco
let antes do trydeclare fora, atribua dentro

Só o que pode falhar

Coloque no try apenas o código que realmente pode falhar: ler um JSON, acessar dados de fora, converter uma entrada. Fica mais fácil saber de onde veio o erro.

Para no primeiro erro

O console.log(resultado) do primeiro exemplo nunca roda: depois do erro, o resto do try é abandonado.

Armadilha: as chaves criam um escopo

let e const declarados dentro do try desaparecem quando o bloco termina. Usar a variável depois dá ReferenceError, fora de qualquer try.

06

Bloco catch: o resgate

O catch captura o erro lançado no try e evita que a aplicação trave. Ele recebe o objeto error, com três propriedades que você vai usar sempre.

consolea chamada fica na linha 10
catch { }sem parâmetro, quando o erro não importa
fallbackuma alternativa quando falha

name e message

name é o tipo do erro (TypeError). message descreve o que deu errado. As duas juntas são o que aparece depois de “Uncaught”.

stack: o rastro das chamadas

Mostra por onde o programa passou até o erro, com a linha de cada função (about:srcdoc:3 é a linha 3 do painel). Não faz parte da especificação oficial, mas todos os navegadores atuais oferecem.

Três ações comuns

No catch você registra o erro (console.error), mostra uma mensagem amigável para quem usa ou tenta uma alternativa (fallback), como no último exemplo.

07

throw: lançando o próprio erro

Dividir por zero em JavaScript dá Infinity, sem erro nenhum. Quando uma situação é inválida para o seu programa, você mesmo lança o erro com throw new Error("mensagem").

consolesem throw, com throw e com throw tratado
TypeError e RangeErrorlance o tipo que explica o problema
throw "texto"funciona, mas perde as informações

throw para tudo, como o return

Depois de um throw, nada mais roda na função. O erro sobe para quem chamou, até encontrar um catch. Se ninguém tratar, vira “Uncaught”.

Escolha o tipo

TypeError para valor do tipo errado, RangeError para número fora do intervalo, Error para o resto. Quem trata pode decidir pelo tipo (seção 10).

Armadilha: lançar um texto

throw "deu ruim" é permitido, mas o catch recebe só um texto: sem name, sem message e sem stack. Lance sempre um objeto: throw new Error("deu ruim").

08

Opcional: o bloco finally

O código dentro do finally sempre é executado, tenha ocorrido um erro ou não. Até quando o erro não é tratado.

sem errotry inteiro, depois finally
com errotry interrompido, catch, depois finally
try...finallysem catch: o finally roda e o erro continua
return no finallyele passa por cima do return do try

Uso comum: devolver o que você pegou

Fechar uma conexão ou um arquivo, esconder o “carregando...”, reativar o botão que foi desativado, registrar o fim da tentativa.

finally não libera memória

Em JavaScript a memória é liberada sozinha pelo coletor de lixo (garbage collector) quando nada mais usa o valor. O finally serve para recursos que você abriu de propósito e precisa fechar.

Armadilha: return dentro do finally

Um return no finally substitui o valor do try e até engole um erro lançado. Deixe o finally só com limpeza, sem return.

09

Exemplo completo: try...catch...finally

Os três blocos juntos numa função. Siga as duas chamadas e repare na ordem em que as linhas aparecem no console.

passo a passodividir(10, 2) e dividir(10, 0)

O finally roda nos dois casos

Com ou sem erro, “Operação finalizada.” aparece. É isso que garante o encerramento da lógica.

Armadilha: a ordem da saída

O resultado aparece depois de “Operação finalizada.”: o return guarda o valor, o finally roda e só então a função devolve. Quem espera ver 5 primeiro se confunde.

null avisa quem chamou

A função não trava o programa e devolve null. Quem chamou confere: if (resultado === null) e decide o que mostrar.

10

Um tratamento para cada tipo

Um catch pega qualquer erro, inclusive os que você não esperava. Pergunte o tipo com instanceof, trate o que você conhece e relance o resto com throw error.

consoleJSON válido, JSON inválido e JSON sem tema

instanceof pergunta o tipo

error instanceof SyntaxError é true para o erro de JSON.parse. Funciona com todos os tipos, inclusive os que você criar (seção 11).

throw error dentro do catch

Relançar devolve o erro para quem chamou, sem perder o tipo, a mensagem e o stack. Na terceira chamada, o TypeError sai da função e vira “Uncaught”.

Armadilha: o catch que esconde bugs

Se o catch devolvesse “CLARO” para qualquer erro, o TypeError da terceira chamada (um bug: falta tratar o JSON sem tema) ficaria escondido para sempre.

11

Erros personalizados

Para erros do seu domínio (cadastro inválido, saldo insuficiente), crie um tipo próprio com class ... extends Error. Ele pode carregar informações extras, como o campo que falhou.

consoleum cadastro certo, três errados
{ cause }um erro novo que guarda o erro original

extends Error

A classe herda message e stack. O super(mensagem) passa a mensagem para o Error; o resto (campo) é seu.

this.name

Sem a linha this.name = "ValidacaoError", o erro aparece como “Error” no console. O nome é o que identifica o tipo para quem lê.

cause: a causa original

Desde 2022, new Error(mensagem, { cause: erro }) embrulha um erro técnico numa mensagem que faz sentido para o seu sistema, sem perder a origem.

12

Erros assíncronos

O try só enxerga erros que acontecem enquanto ele está rodando. Um erro que acontece depois (num setTimeout ou numa promessa) escapa, a não ser que você use await.

setTimeout dentro do tryo erro acontece depois: escapa
try dentro do setTimeouto try roda junto com o erro: captura
consolea busca leva 0,8 s; o id 0 não existe

await traz o erro para dentro do try

Com await, a função espera a promessa. Se ela falhar, o erro é lançado ali, na linha do await, e o catch pega.

.catch() é o equivalente sem await

Com .then(), o tratamento vai no .catch() da promessa. Sem nenhum dos dois, aparece “Uncaught (in promise)”.

Armadilha: fetch não lança em 404

O fetch só falha quando não há resposta (sem rede, servidor fora do ar). Um 404 ou um 500 chegam como resposta normal: confira resposta.ok e lance o erro você mesmo.

13

Boas práticas: não silencie, seja específico

Nunca deixe o bloco catch vazio: registre o erro ou tome uma ação corretiva. E envolva no try apenas o que realmente pode falhar.

evite
catch vazioa segunda nota sumiu sem aviso
prefira
catch que registrae avisa quem chamou
evite
try gigantequal das linhas falhou?
prefira
try específicocada falha com o seu tratamento

Silêncio é o pior erro

Um catch vazio transforma um problema visível em um dado perdido que ninguém sabe explicar. No mínimo, console.error.

Específico é mais fácil de depurar

No try gigante há dois problemas diferentes (o JSON do usuário e o config.itens que não existe) e uma mensagem só.

Armadilha: try...catch como esconderijo

config.itens.length não é um erro de entrada: é um bug. Ele se resolve com uma condição no código, não com um catch.

14

Feedback amigável para quem usa

Em aplicações visuais, mostre ao usuário uma mensagem clara do que fazer, em vez do erro técnico do console. O erro técnico continua registrado, para quem programa.

previewteste 11, abc, 8,5 e o campo vazio

Duas mensagens, dois públicos

O console recebe o tipo e o detalhe técnico. A tela recebe o que fazer, na língua de quem usa, sem “TypeError” nem “NaN”.

role="alert"

Leitores de tela anunciam a mensagem assim que ela muda. A cor ajuda, mas a mensagem precisa fazer sentido sem ela.

Armadilha: error.message na tela

Mostrar a mensagem técnica (“Cannot read properties of undefined”) assusta quem usa e pode expor detalhes internos do sistema.

15

Registro e monitoramento

Use console.error ou ferramentas de monitoramento para registrar falhas em produção. Como último recurso, a página pode ouvir todo erro que ninguém tratou.

consoleos ouvintes registram e o erro continua aparecendo

Ferramentas de monitoramento

Serviços como Sentry, New Relic e Datadog fazem isso por você: recebem os erros dos navegadores dos usuários, agrupam e avisam a equipe.

console.error, não console.log

No F12, console.error aparece em vermelho, com o caminho das chamadas, e pode ser filtrado. Um erro registrado como log comum se perde.

Armadilha: dados pessoais no registro

Nunca registre senha, CPF ou cartão junto com o erro. Pela LGPD, o registro também é tratamento de dados pessoais.

16

Validando entradas

Confira os dados na entrada da função e lance um erro claro antes que um valor ruim se espalhe. O cuidado está em escolher a verificação certa.

typeof e Number.isFiniteNaN e Infinity são do tipo number
validarIdadetipo, depois intervalo

Valide cedo

As verificações ficam no começo da função, uma por condição, cada uma com o seu throw. O resto da função pode confiar nos dados.

Tipo primeiro, intervalo depois

TypeError quando o valor nem é número; RangeError quando é número mas está fora do aceitável. Quem trata sabe o que dizer em cada caso.

Armadilha: typeof NaN é "number"

typeof nota !== "number" deixa passar NaN e Infinity, que chegam de Number("abc") e de divisões por zero. Number.isFinite e Number.isInteger recusam os dois.

Atividade

Validando entradas e dados externos

Duas funções que não podem derrubar o programa: uma que calcula a média de duas notas (individual) e uma que carrega usuários de um servidor que falha metade das vezes (em equipe).

Parte 1 · obrigatória

O que as funções precisam fazer

  • Individual: crie calcularMedia(nota1, nota2) usando try...catch.
  • Valide se as notas são números com typeof nota !== "number" e lance throw new Error("mensagem") se não forem.
  • Garanta que as notas estão entre 0 e 10; fora disso, lance um Error.
  • No catch, mostre o erro com console.error e retorne null.
  • Em equipe: criem carregarUsuarios(), que simula um servidor com 50% de chance de falha (Math.random() < 0.5 lança um erro).
  • Usem try...catch: com sucesso, retornem a lista de nomes; com erro, retornem um array vazio [].
  • Usem finally para registrar o fim da tentativa.
Parte 2 · desafio

Exigências que quebram a solução preguiçosa

  • calcularMedia(NaN, 8) e calcularMedia(-1, Infinity) retornam null. O typeof sozinho não basta.
  • Lance TypeError quando a nota não é número e RangeError quando está fora de 0 a 10, e a mensagem diz qual nota (nota1 ou nota2) e o valor recebido.
  • carregarUsuarios passa a devolver uma Promise que demora 0,5 s (com setTimeout) e é chamada com await dentro de try...catch.
  • Antes de desistir, carregarUsuarios tenta até 3 vezes; cada tentativa registra o próprio fim no finally. Só depois da terceira falha retorna [].
  • Crie a classe ServidorError extends Error para a falha simulada e trate com instanceof; qualquer outro erro é relançado.
  • Proibido: catch vazio, throw de texto e return dentro do finally.
Parte 3 · investigação

Responda em comentário no próprio código

  • Por que typeof NaN é "number"? Que chamada de calcularMedia passaria pela sua validação da Parte 1 e daria um resultado errado?
  • O que muda se o return null for para dentro do finally? Teste com calcularMedia(7, 9).
  • Chame carregarUsuarios() da Parte 2 sem await, dentro de um try. O catch é acionado? O que aparece no console e por quê?
  • Se o próprio atividade.js tiver um erro de sintaxe, por que nenhum catch do arquivo é acionado?
  • Lançar um erro ou retornar null: o que muda para quem chama calcularMedia? Quando cada um é melhor?

Entrega

O arquivo atividade.js com as duas funções, as chamadas de teste e as respostas da Parte 3 em comentários. A parte em equipe leva o nome de todos no topo do arquivo.

Critério técnico

Nenhuma chamada de teste derruba o programa; todo erro tem tipo, mensagem e console.error; o finally aparece em todas as tentativas, com ou sem falha.

Critério de clareza

As mensagens de erro dizem o que estava errado e o que era esperado (“nota2 precisa estar entre 0 e 10, recebi 11”), não só “erro”.

Bom código!

Erro vai acontecer. A diferença é quem fica sabendo: o usuário, com uma tela que não responde, ou você, com uma mensagem clara.
